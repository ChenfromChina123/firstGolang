# 2026-07-07 视频多画质预览优化

## 任务目标
用户要求实现视频预览的画质选择功能：
- 当前实现：原画质流式预览（支持 HTTP Range 按需加载）
- 用户需求：可自主选择画质观看，默认中等画质

## 实施方案

### 后端
- **`internal/storage/thumbnail.go`** 新增：
  - `findFFmpeg()` 函数：优先用 `FFMPEG_PATH` 环境变量解析 ffmpeg 路径，回退到 `exec.LookPath`
  - `transcodeSpec` 类型 + `transcodeSpecMap` 三档规格表：
    - high=1080p CRF20 / medium=720p CRF23 / low=480p CRF26
  - `TranscodeExists(basePath, fileID, quality)` 缓存命中检查
  - `GenerateTranscode(basePath, srcPath, fileID, quality)` 调用 ffmpeg 转码为 mp4(H.264+AAC)，
    使用 `movflags +faststart` 支持浏览器边下边播
  - `GeneratePoster` 同步改用 `findFFmpeg`，统一 ffmpeg 路径解析

- **`internal/handler/preview.go`** 修改：
  - `serveMeta` 视频类型附加 `video_high/medium/low` 三个 URL（指向 `/transcode?quality=xxx`）
  - 实现 `case "transcode"` → `serveTranscode(w, r, fileID)`
  - `serveTranscode` 流程：
    1. 解析 quality 参数（默认 medium）
    2. high 直接 fallback 到 `serveContent`（无需转码，避免无意义重编码）
    3. medium/low 命中缓存直接流式返回，未命中同步调 ffmpeg 转码（首次会等待）
    4. 支持 HTTP Range（与 serveContent 同款实现）

### 前端
- **`web/app.js`** 修改：
  - `renderVideo` 复用顶部 `#preview-quality` 选择器：
    - 动态替换选项为「高画质/中画质/低画质」（默认 medium）
    - onchange 切换画质时保存 `currentTime/playbackRate/paused` 状态
    - 重设 src 后等 `loadedmetadata` 事件恢复进度
  - `renderImage` 重置选项为「小/中/大」，防止视频预览污染选项

### API
- `GET /api/preview/{id}/transcode?quality=high|medium|low`（支持 Range）
- `GET /api/preview/{id}` meta 返回 `video_high/medium/low` 三个 URL
- `high` 直接 fallback 到原文件 `serveContent`（无需转码）

## 重要发现

### ffmpeg 环境变量
- 用户本地 ffmpeg 在 `D:\下载\ffmpeg-master-latest-win64-gpl\ffmpeg-master-latest-win64-gpl\bin\ffmpeg.exe` 未加 PATH
- 解决方案：新增 `FFMPEG_PATH` 环境变量支持，部署时不强制改 PATH
- 生产环境（Linux）可 `export FFMPEG_PATH=/usr/local/bin/ffmpeg` 或加入 PATH

### 本地 server 启动方式
```powershell
$env:FFMPEG_PATH = "D:\下载\ffmpeg-master-latest-win64-gpl\ffmpeg-master-latest-win64-gpl\bin\ffmpeg.exe"
$env:PORT = "8090"
$env:DATA_DIR = ".\test_local\transcode_test\_data_e2e"
$env:JWT_SECRET = "test_secret_for_transcode_e2e"
$env:STORAGE_TYPE = "local"
$env:FILESYNC_INITIAL_USERNAME = "admin"
$env:FILESYNC_INITIAL_PASSWORD = "Admin12345"
$env:ALLOWED_REFERERS = "localhost:8090,127.0.0.1:8090"  # 必须，否则 referer 中间件拦截 /web/app.js
.\filesync_server.exe
```

### Referer 中间件配置
- 预先存在的部署配置：本地 localhost 访问需配置 `ALLOWED_REFERERS=localhost:8090`
- 否则浏览器请求 /web/app.js 时 Referer=localhost:8090 不在白名单会被 403 拒绝

### 部署到服务器注意事项
1. 服务器需安装 ffmpeg（Ubuntu: `apt install ffmpeg`）
2. 配置 `FFMPEG_PATH` 或确保 ffmpeg 在 PATH
3. `ALLOWED_REFERERS` 加入生产域名（如 aistudy.icu）

## 转码耗时与缓存
- 转码是同步阻塞操作（首次请求 medium/low 时 ffmpeg 转码，可能耗时数秒到数分钟）
- 转码完成后缓存到 `{basePath}/_transcoded/{fileID}/{quality}.mp4`
- 后续请求直接流式返回缓存（毫秒级响应）
- 缓存命中后无任何 ffmpeg 调用开销

### 发现的生产环境问题

#### 问题 1：OOM kill（并行 ffmpeg 触发）
- 服务器仅 1.8GB RAM
- 浏览器重试/并发请求触发多个 ffmpeg 进程并行运行
- 3 个 ffmpeg 同时运行触发 OOM killer
- 日志：`signal: killed`

#### 问题 2：部分文件残留（损坏文件被后续请求读取）
- ffmpeg 被 kill 后，部分写入的 medium.mp4 残留
- 下次请求 `TranscodeExists` 返回 true（文件存在）
- 浏览器读到损坏文件触发 `DEMUXER_ERROR_COULD_NOT_OPEN`

### Bug 修复（commit b9e57cc）

**修改文件**：`internal/storage/thumbnail.go`

1. **单飞锁 `transcodeInFlight`**（`sync.Map`）
   - key: `"fileID:quality"`
   - 同一 fileID+quality 的转码请求串行化
   - 持锁后二次检查文件是否已生成（避免重复执行）

2. **全局信号量 `transcodeGlobalSem`**（`chan struct{}, 1`）
   - 限制服务器同时仅 1 个 ffmpeg 进程
   - 防止不同 fileID 的并行转码触发 OOM

3. **失败清理**
   - `cmd.Run()` 失败时 `os.Remove(dstPath)` 删除部分文件
   - 防止下次请求读到损坏文件

4. **`-threads 1`** 参数
   - 限制 ffmpeg 单线程编码
   - 降低内存峰值（防 OOM kill）

### 默认画质改为高画质（commit d2b7025）

**修改文件**：`web/app.js` `renderVideo` 函数

## 异步转码方案实施（2026-07-07 续 2）

### 目标
解决"已知限制"：首次切换中/低画质时 `serveTranscode` 同步调用 ffmpeg 转码（45MB 视频约 54s），HTTP 响应阻塞导致浏览器超时报 `DEMUXER_ERROR_COULD_NOT_OPEN`。

### 实施方案
将同步转码改为**异步转码 + 前端轮询进度**：
- 缓存未命中时返回 `202 Accepted + status_url`（前端轮询）
- 后台 goroutine 执行 ffmpeg 转码
- 前端显示进度条，2s 间隔轮询 `transcode-status`
- 转码完成后自动加载视频流

### 后端变更

#### `internal/storage/thumbnail.go` 新增异步任务管理
- `TranscodeJobStatus` 类型 + 4 个常量（pending/running/done/failed）
- `TranscodeJob` 结构（含 `sync.RWMutex` 保护 Status/Error 并发读写）
- `transcodeJobs sync.Map` 全局任务表
- `StartTranscodeJob` 函数：
  - `LoadOrStore` 占位 job（修复 TOCTOU 竞态）
  - 检查磁盘缓存 → 命中则原子改 status=done
  - 失败重试机制（RetryCount，上限 3 次）
  - 启动 goroutine 执行 `GenerateTranscode`
- `GetTranscodeJob` 函数（只读查询）
- `scheduleJobCleanup` 函数（TTL 清理：done 5min / failed 30min）
- `GenerateTranscode` 改用临时文件 `.part.mp4` + 原子 `os.Rename`（修复竞态条件）

#### `internal/handler/preview.go` 拆分 serveTranscode
- 缓存命中 → `serveTranscodeFile`（流式返回，支持 Range 206）
- 未命中 → `StartTranscodeJob` → 返回 202 + JSON（含 status_url）
- 新增 `serveTranscodeStatus` 查询端点（先查磁盘缓存再查 job）

### 修复的 3 个 Bug

#### Bug 1：死锁（StartTranscodeJob goroutine 与 GenerateTranscode 重复获取信号量）
- **现象**：`TestStartTranscodeJob_ConcurrentSameKey` 60s 超时
- **根因**：goroutine 先获取 `transcodeGlobalSem`（缓冲=1），然后调用 `GenerateTranscode`，而 `GenerateTranscode` 内部也尝试获取同一个信号量 → 永久阻塞
- **修复**：移除 goroutine 内部的信号量获取，由 `GenerateTranscode` 内部统一管理

#### Bug 2：竞态条件（浏览器读到部分写入的转码文件）
- **现象**：切换中画质后 `video.error.code=4`（DEMUXER_ERROR_COULD_NOT_OPEN）
- **根因**：`GenerateTranscode` 直接写入 `dstPath`，浏览器在文件写入过程中请求到不完整数据
- **修复**：改为写入临时文件 `dstPath + ".part.mp4"`，完成后 `os.Rename` 原子替换

#### Bug 3：ffmpeg 无法识别 `.mp4.tmp` 扩展名
- **现象**：`Error: Unable to choose an output format for 'medium.mp4.tmp'`
- **根因**：ffmpeg 通过文件扩展名推断输出格式，`.mp4.tmp` 不是标准扩展名
- **修复**：临时文件改用 `.part.mp4` 后缀（保留 `.mp4` 后缀让 ffmpeg 识别）
